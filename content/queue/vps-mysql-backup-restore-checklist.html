MySQL Backup and Restore on a VPS: Checklist

Short answer: back up with mysqldump or a physical backup tool, copy the backup off the server, and restore it on a spare machine on a schedule — because a backup that has never been restored is an assumption, not a safety net. The most common MySQL data-loss story is not "we had no backup" — it is "we had backups, and every one of them was corrupt, incomplete, or stored on the same disk that failed." The checklist below closes that gap.

Backups have two enemies: the disk that dies with the database, and the restore nobody ever rehearsed. Fixing the first is a copy command; fixing the second is a habit. Both are cheap compared with rebuilding a database from memory.

1. Take a consistent logical backup with mysqldump

For most small and medium databases, a logical dump is the simplest reliable backup. Use --single-transaction so InnoDB tables are dumped in a consistent state without locking the database for the whole run: 

mysqldump --single-transaction --routines --triggers --all-databases | gzip > /backup/mysql-$(date +%F).sql.gz

Include routines and triggers — a dump without them restores the tables but silently drops the stored procedures your application depends on. For very large databases, a physical backup tool such as Percona XtraBackup or a filesystem snapshot may be faster, but the principle is the same: the backup has to capture a consistent point in time, not a moving target.

2. Copy the backup off the server, on a schedule

A backup on the same disk as the database protects against a bad query, not against a dead disk. Copy each backup to another location — another server, object storage, or an external drive — and automate the copy so it happens whether or not anyone remembers: 

rsync -av /backup/ user@203.0.113.10:/backup/mysql/

Replace the address with your own backup destination. Keep more than one generation: a single latest copy is useless if the corruption you are recovering from is already inside it. Our offsite backup rotation checklist covers retention windows and how many generations to keep.

3. Restore on a spare machine and check the data, not just the exit code

A restore that exits without an error is not proof the data is good. Rehearse the restore on a separate server or container, then check that the important parts are actually there: 

gunzip < /backup/mysql-2026-11-26.sql.gz | mysql -u root -p
mysql -u root -p -e "SELECT COUNT(*) FROM mydb.orders;"

Compare row counts and a few known records against the live database. A dump that restores with zero errors but missing tables — because a table was dropped mid-dump, or a privilege was missing — is worse than no backup at all, because it delays the moment you discover the problem. Schedule the rehearsal monthly at minimum, and after any change to the backup command.

4. Protect the backup itself

A database dump contains everything an attacker wants: user emails, password hashes, and any data your application stores. Restrict the backup directory to the database user and root, encrypt backups that leave the server, and keep the credentials used by the backup script in a file only root can read. Our snapshot restore test guide covers the same verification habit at the whole-server level — snapshots and database backups complement each other, and neither replaces the other.

5. Automate it, and alert on failure

A backup that runs only when someone remembers to run it will eventually not run. Put the dump and the offsite copy in a scheduled job, log the output, and alert on a non-zero exit code — a silent backup failure is the same as no backup. Check the backup size as a sanity signal too: a dump that suddenly shrinks to near zero usually means the dump failed and gzip compressed an error message instead of data.

Checklist before you move on

  • Logical dump taken with --single-transaction, including routines and triggers.
  • Backup copied off the server automatically, with more than one generation kept.
  • Restore rehearsed on a spare machine; row counts and known records verified.
  • Backup files restricted to root, encrypted if they leave the server.
  • Dump and copy automated, with an alert on any failure and a size check as a sanity signal.

The test that matters is the one you run before you need it. If the last restore rehearsal was more than a month ago, run one today — it is a thirty-minute job on a quiet afternoon, and a multi-day rebuild on the day it is not.

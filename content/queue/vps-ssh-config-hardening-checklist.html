VPS SSH Hardening Checklist: Lock Down sshd_config

Short answer: disable password login and root login, allow only key login for named users, restrict the SSH port behind your firewall, and put fail2ban in front of what is left — then test the new config in a second session before you close the first one. Most SSH break-ins are not clever: they are automated password guesses against a server that still accepts them. The checklist below removes the guesses, the root target, and the open door, in the order that keeps you from locking yourself out.

This assumes you already log in with a key at least some of the time. If you have never set up key login, do that first — our SSH key rotation guide covers generating a key pair and replacing a key safely, and the steps below assume the key is already in place.

1. Back up the config and keep one session open

Before changing anything, copy the current config and keep your existing SSH session connected while you test: 

cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak
sshd -t

The backup is your undo button, and sshd -t checks the syntax before the daemon ever reads the file. Open a second SSH session and leave the first one connected — if the new config has a mistake, the old session is still your way back in. Never restart SSH from your only session without a tested fallback: a typo in sshd_config can refuse every new connection, and the recovery path is the provider console, as our SSH lockout recovery guide explains.

2. Turn off password and root login

These three settings do most of the work. Edit /etc/ssh/sshd_config: 

PasswordAuthentication no
PermitRootLogin no
PubkeyAuthentication yes

With password login off, a guesser can try forever and never get a prompt that accepts a password. With root login off, the most valuable account on the box is not reachable over SSH at all — log in as a normal user and use sudo. Challenge-response and keyboard-interactive logins should go off too if you do not use them; each one is another door that key-only login does not need.

3. Limit who can log in at all

Even with keys only, restrict SSH to the accounts that need it: 

AllowUsers deploy
MaxAuthTries 3
LoginGraceTime 30

AllowUsers means an attacker who somehow obtains a key for another account still cannot use it over SSH. MaxAuthTries 3 cuts off a connection after three failed attempts, and a short grace time stops half-open connections from lingering. If your server has service accounts that never log in interactively, they should not be in the allowed list — and they should have their shells set to a non-login shell as well.

4. Change the port only as a second layer, not the first

Moving SSH off port 22 cuts the volume of automated scans dramatically, but it is noise reduction, not security — a port scan finds the new port in seconds. Change it only after key-only login is working, and update the firewall rule at the same time so the new port is the only one open: 

Port 2222

Our SSH port change checklist covers the firewall update and the testing sequence in detail — the common mistake is changing the port in the config but forgetting the firewall, which leaves the server unreachable instead of merely quieter. And if you use fail2ban, remember to point it at the new port, or it will be watching a door nobody knocks on.

5. Put fail2ban in front of what is left

With key-only login, fail2ban is a tripwire rather than the main defence: it bans addresses that hammer the service, which keeps the logs readable and the load down. Our fail2ban SSH guide covers the jail setup; the two settings that matter most here are a short ban after a few failures and a ban long enough that a bot moves on. Check the fail2ban log after a day — if it is empty, either the hardening worked or the jail is not watching the right port, and you should find out which.

6. Restart, test from a second session, then verify

Apply the change and prove it works before you trust it: 

systemctl restart sshd
ssh -p 2222 deploy@203.0.113.10
ssh -o PreferredAuthentications=password deploy@203.0.113.10

The first command should connect with your key. The second should fail outright — that failure is the proof password login is really off. Then check the auth log for anything unexpected, and confirm your firewall still allows only the intended port: our firewall first-steps guide is the reference for what a new server should expose. Keep the backup config for a week; if nothing breaks in that time, the new settings are the baseline.

Checklist before you move on

  • Config backed up, syntax checked with sshd -t, and an old session kept open during the change.
  • Password login off, root login off, key login on — verified by a failed password attempt.
  • AllowUsers set to only the accounts that need SSH; MaxAuthTries low.
  • Port changed only after key login works, firewall updated to match.
  • fail2ban watching the right port, with bans visible in its log.
  • Restart tested from a fresh session before the old session is closed.

Hardened SSH is quiet SSH: the logs stop filling with guesses, and the only logins left are yours. If the auth log is still noisy after this checklist, something in the list above is not actually in force — re-read the running config, not the file you think you edited.

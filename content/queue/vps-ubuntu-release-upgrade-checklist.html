Ubuntu Release Upgrade on a VPS: Checklist

Short answer: back up and snapshot first, bring the current release fully up to date, check free disk space and third-party repositories, run the upgrade in a session that survives a disconnect, and verify every service before calling it done. A release upgrade is not a routine package update — it replaces the operating system underneath your services. Most upgrades go smoothly; the ones that do not are the ones started without a way back.

The deciding question before you begin is not "will this work" but "what happens if it does not." If the answer is a tested snapshot you can restore in minutes, the upgrade is a reasonable risk. If the answer is nothing, stop and fix that first.

1. Back up, then snapshot — in that order

Take a full backup of anything you cannot rebuild: website files, databases, and configuration in /etc. Copy it off the server, not just to another directory on the same disk. Then take a provider snapshot of the whole machine. Our offsite backup rotation checklist covers keeping a copy outside the server, and our snapshot restore test guide covers proving the snapshot actually restores — a snapshot you have never restored is a hope, not a plan.

Confirm the snapshot finished before starting the upgrade. A snapshot still in progress when the upgrade begins may capture a half-upgraded system, which is the worst state to restore from.

2. Bring the current release fully up to date

The upgrade tool expects the current release to be current. Update all packages and reboot if a new kernel was installed, so the upgrade starts from a known-good, running system: 

sudo apt update && sudo apt full-upgrade -y
sudo reboot

Also check which release you are on and whether an upgrade path exists — not every release can jump directly to the newest one, and some require stepping through an intermediate release. Confirm the target release and the supported path before running the upgrade command, not during it.

3. Check disk space and third-party repositories

A release upgrade downloads hundreds of packages and needs free space to unpack them. Check available space on the root filesystem and free some if it is tight — our disk space cleanup checklist covers the usual suspects. Running out of space halfway through an upgrade is one of the few ways to turn a routine upgrade into a rescue operation.

List third-party repositories and PPAs. The upgrade tool usually disables them, which means software installed from them may not upgrade, or may be removed. Note which services depend on third-party packages and check that they have packages for the target release — if they do not, decide before the upgrade whether to keep the old release, drop that software, or find a replacement.

4. Run the upgrade in a session that survives a disconnect

Start the upgrade inside a terminal multiplexer such as tmux or screen, so a dropped connection does not kill it halfway: 

tmux new -s upgrade
sudo do-release-upgrade

If the connection drops, reconnect and reattach the session instead of starting over. During the upgrade, the tool will ask about configuration files you have modified — read each prompt rather than accepting defaults blindly. A wrong choice here can overwrite a working service configuration with a stock one, and the service will fail to start afterwards for a reason that looks unrelated to the upgrade.

5. Verify every service before calling it done

After the upgrade and reboot, go through the services one by one: web server, database, cron jobs, firewall, and any application that runs on boot. Check that each one is running and serving correctly, not just that the system booted: 

systemctl --failed
ss -tlnp

The first command lists failed units; the second shows what is actually listening. Compare the listening services against what ran before the upgrade — a missing listener is a service that did not survive it. Check the site from the outside, not just from the server: a page fetched from your own machine proves the public path works. And confirm scheduled jobs still run — a cron job that silently stops after an upgrade can go unnoticed for weeks.

Checklist before you move on

  • Off-server backup taken and snapshot completed before the upgrade starts.
  • Current release fully updated and rebooted into a known-good state.
  • Upgrade path to the target release confirmed as supported.
  • Enough free disk space on the root filesystem for the package download.
  • Third-party repositories reviewed; services depending on them checked for the target release.
  • Upgrade run inside tmux or screen so a disconnect cannot kill it.
  • Every service verified after reboot: failed units, listening ports, and an outside check of the site.

If the upgrade fails partway, do not keep patching forward in the hope it recovers — restore the snapshot, find out what went wrong on a test machine, and try again with the fix in place. The snapshot is there so a failed upgrade costs an hour, not a weekend.

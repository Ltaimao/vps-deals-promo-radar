VPS High Load Average: Diagnose It Step by Step

Short answer: read the 1-, 5-, and 15-minute load numbers, compare them with your CPU count, then check CPU usage, memory pressure, disk wait, and the process list — in that order — before deciding whether the fix is a runaway process, more memory, or a bigger box. A load average of 8 means very different things on a 1-core VPS and an 8-core one, and most of the panic it causes comes from reading the number without that context. The steps below turn the number into a cause.

This is a diagnosis guide, not a sizing guide: it tells you what is slow and why. If the diagnosis points at a box that is simply too small, the sizing decision is a separate one — but do not buy a bigger box until the steps below have ruled out a single misbehaving process, which is the most common cause by far.

1. Read the three numbers against your CPU count

Start with uptime and your core count: 

uptime
nproc

The three load numbers are the 1-, 5-, and 15-minute averages of runnable and uninterruptible processes. As a rule of thumb, a load around the core count means the box is busy but keeping up; a load several times the core count means work is queueing. Compare the three numbers too: 1-minute high and 15-minute low means a spike that is already passing, while all three climbing together means a sustained problem. A short spike after a reboot or a backup run is normal; a load that stays above your core count for an hour is not.

2. Check whether the CPU is actually busy

A high load with an idle CPU points somewhere else entirely — often disk wait. Look at both: 

top -b -n 1 | head -20
vmstat 1 3

In top, the %Cpu(s) line separates user time, system time, and wait time (wa). High user time with one process at the top of the list is a runaway process or a legitimately heavy job. High wait time means processes are stuck waiting on disk, which is a storage problem, not a CPU problem. On a shared VPS, also check steal time — our CPU steal time guide explains how to tell when the host, not your box, is the bottleneck.

3. Check memory before blaming the CPU

When memory runs out, the kernel swaps, and swapping processes pile up in the load average while the CPU idles. Check both: 

free -h
swapon --show

If available memory is near zero and swap is in active use, the load is a memory symptom. Our swap versus RAM guide covers how to read these numbers and what counts as real pressure versus the kernel using spare memory for cache. The fix for genuine memory pressure is usually fewer services, a smaller footprint per service, or more RAM — not a faster CPU.

4. Find the process — or processes — responsible

Once you know which resource is scarce, name the consumer: 

ps aux --sort=-%cpu | head -10
ps aux --sort=-%mem | head -10

One process eating a whole core is usually a stuck job, a runaway script, or a backup that started at the wrong hour — check its start time and its parent before killing it, because restarting a service that a cron job will immediately relaunch fixes nothing. Many small processes adding up to the same load usually means a traffic spike or a job queue that has grown faster than the workers draining it. Either way, write down the process name and its resource use before you act: the fix for a runaway cron job and the fix for a traffic spike are different fixes.

5. Rule out disk wait and the usual suspects

If the CPU is idle, memory is fine, and no process stands out, look at disk: 

iostat -x 1 3
df -h

High %util or long await times in iostat mean the disk cannot keep up — a backup writing, a database checkpointing, or a log file growing without rotation. A full disk makes this worse in sudden ways; our disk space cleanup checklist covers the fast wins when the disk is the problem. Also check the obvious: a backup or update job running in the middle of the day, and the cron table for anything scheduled hourly that should be daily.

Checklist before you move on

  • Load read against the core count, with the 1-, 5-, and 15-minute trend noted.
  • CPU, wait time, and steal time separated — you know which one is high.
  • Memory and swap checked; swapping ruled in or out.
  • The responsible process (or job queue) named, with its start time and parent checked.
  • Disk wait and disk space ruled out; cron jobs reviewed for a bad schedule.
  • Diagnosis written down before any fix — so the fix matches the cause, not the symptom.

A load average is a queue length, and queues have causes. If the number is high and every check above comes back clean, the cause is usually the host or a neighbour — re-check steal time, and take the numbers to your provider instead of guessing at a bigger plan.

WireGuard VPN on a VPS: Setup Checklist

Short answer: install WireGuard, generate a key pair for the server and one for each client, write a small server config and a matching client config, open a single UDP port in the firewall, enable forwarding, and test the tunnel from a client before you depend on it. WireGuard has no sprawling config files and no certificate authority to run — the whole server setup fits in a few lines, and most of the work is getting the keys and the firewall right.

This covers a personal VPN on a VPS you control: one server, a few clients, traffic routed through the server. Before you start, check that running a VPN fits your provider's terms and your use case — our running a VPN on a cheap VPS guide covers the practical limits, including the small plans where a VPN competes with everything else for the same CPU.

1. Install WireGuard and generate the keys

Install the tools, then generate a key pair for the server. Keys are the whole authentication system — there are no passwords to manage: 

apt install wireguard
umask 077
wg genkey | tee /etc/wireguard/privatekey | wg pubkey > /etc/wireguard/publickey

Keep the private key readable only by root — the umask 077 before generating it takes care of that. Generate a separate key pair for each client the same way, and keep a note of which public key belongs to which device. A client key that is shared between two devices is two devices with one identity, which makes revoking one of them impossible without revoking both.

2. Write the server config

The server config is short. Use an address range that does not collide with your home network — the documentation range 10.6.0.0/24 is a common choice: 

[Interface]
Address = 10.6.0.1/24
ListenPort = 51820
PrivateKey = <server private key>

[Peer]
PublicKey = <client public key>
AllowedIPs = 10.6.0.2/32

AllowedIPs on the server is both the routing table and the access list: the peer may only send traffic from the address listed here, and only traffic for that address is routed to it. Add one [Peer] block per client. If a client's address changes — a phone moving between networks — the server does not care, because WireGuard identifies peers by key, not by address.

3. Open one UDP port and enable forwarding

WireGuard needs exactly one port, UDP. Open it in the firewall and turn on forwarding so the server can pass traffic between the tunnel and the internet: 

ufw allow 51820/udp
sysctl -w net.ipv4.ip_forward=1

The forwarding setting does not survive a reboot unless you make it permanent in /etc/sysctl.conf — a server that works until the first reboot and then silently stops routing is a classic WireGuard gotcha. Our firewall first-steps guide is the reference for keeping the rest of the server closed while this one port stays open. If your VPS also has an IPv6 address, decide now whether the tunnel carries IPv6; our IPv6-only VPS guide covers the addressing questions that come with that choice.

4. Write the client config and test before you trust it

The client config mirrors the server, with the server's public key and the server's public address — here shown with the documentation address 203.0.113.10 as a placeholder for your server's real IP: 

[Interface]
Address = 10.6.0.2/24
PrivateKey = <client private key>
DNS = 10.6.0.1

[Peer]
PublicKey = <server public key>
Endpoint = 203.0.113.10:51820
AllowedIPs = 0.0.0.0/0
PersistentKeepalive = 25

AllowedIPs = 0.0.0.0/0 routes all of the client's traffic through the tunnel; a narrower range routes only the tunnel addresses. PersistentKeepalive keeps the connection alive through home routers that forget idle UDP sessions. Bring the server up with wg-quick up wg0, start a client, and check with wg show that the handshake completed and traffic flows both ways — then visit a site that shows your public address and confirm it is the server's, not your own.

5. Make it survive a reboot and watch it

Enable the interface at boot, and add the tunnel to whatever monitoring you already run: 

systemctl enable wg-quick@wg0
wg show

A tunnel that dies quietly is worse than one that never started, because the client keeps sending traffic into a dead end. Our uptime monitoring guide covers alerting on the services that matter — add a check that the WireGuard handshake is recent, not just that the server answers a ping. Keep the private keys backed up off the server, and when a device is lost or retired, delete its [Peer] block and restart the interface.

Checklist before you move on

  • WireGuard installed; server and client key pairs generated, private keys root-only.
  • Server config written: one [Peer] per client, each with its own tunnel address.
  • Single UDP port open in the firewall; forwarding enabled and made permanent.
  • Client config tested end to end: handshake completes, traffic flows, public address is the server's.
  • Interface enabled at boot; handshake age monitored; keys backed up off the server.
  • Lost or retired devices removed from the server config — keys are per device, never shared.

A WireGuard setup that works the first time usually keeps working — the moving parts are few, and the failure modes are mostly a wrong key, a closed port, or a forwarding setting that did not survive a reboot. When the tunnel stops, check those three first.

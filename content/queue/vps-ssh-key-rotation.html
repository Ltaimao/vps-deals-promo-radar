VPS SSH Key Rotation: Replace a Compromised Key Safely

Short answer: add the new key first, test it from a second session, and only then remove the old key. The order is the whole trick — a key you delete before testing its replacement is how a routine rotation turns into a lockout. If the old key may be compromised, move fast but in the same order: add, test, remove, then check the server for anything the old key may have left behind.

This guide assumes key login is already in use. If the server still accepts password login, rotating the key alone does not close that door — disabling password authentication is a separate step, and it belongs after the new key is proven to work, for the same reason: never remove an access path before the replacement is tested.

1. Make the new key on your own machine

Generate the key pair where you sit, not on the server. A private key should never travel over the network, and generating it on the server means downloading it afterwards — which is exactly the transfer you want to avoid: 

ssh-keygen -t ed25519 -C "laptop-2026-11"

The -C comment is not decoration: it is the label that lets you tell keys apart later, when you are staring at a list of fingerprints trying to work out which one to remove. Name it after the device, not the server. Ed25519 works on any reasonably current OpenSSH; if an old client refuses it, RSA with 4096 bits is the fallback, not a reason to keep using the old key.

2. Add the new public key — append, never overwrite

Only the .pub half ever leaves your machine. Append it to the server's authorized keys: 

ssh-copy-id -i ~/.ssh/id_ed25519.pub root@203.0.113.10

ssh-copy-id appends the key and fixes the permissions for you. If you copy the line by hand instead, append it — do not overwrite the file. Overwriting ~/.ssh/authorized_keys with a single key silently removes every other key in it, including the one you are currently logged in with. After adding, check the permissions if login fails: the .ssh directory should be 700 and authorized_keys 600, both owned by the login user. OpenSSH ignores keys in a file it considers too open.

3. Test the new key from a second session

Open a new terminal and log in with the new key while your first session is still connected: 

ssh -i ~/.ssh/id_ed25519 root@203.0.113.10

If the new session connects, the new key works and the rotation can continue. If it fails, the first session is still there to fix the problem — wrong key file, wrong permissions, or a key line pasted with a line break in the middle are the usual causes. Do not touch the old key until this test passes. If you do lock yourself out anyway, the recovery route is the provider console, as covered in our VPS SSH lockout recovery guide.

4. Remove the old key — exactly one line

Find the old key's fingerprint first, so you remove the right line and nothing else: 

ssh-keygen -lf ~/.ssh/id_old.pub

Match that fingerprint against the lines in ~/.ssh/authorized_keys — each line ends with the comment you set when the key was made, which is why step 1's label matters. Delete exactly that one line, save, and then prove the old key is dead by trying it: 

ssh -i ~/.ssh/id_old root@203.0.113.10

This time a failed login is the result you want. If the old key still connects, the line you removed was not the one the server was accepting — check for a second copy of the key in another user's authorized_keys, or a key the provider's panel injects at boot.

5. If the old key may be compromised, check for footprints

A compromised key is not just a key to replace — it may have been used, and the server can usually tell you whether it was. Check the same four places before you call the rotation done: 

cat ~/.ssh/authorized_keys
last
sudo grep sshd /var/log/auth.log

Look for keys you do not recognize in authorized_keys, logins at times you were not working in last, and accepted logins for the old key in the auth log — the path varies by distribution, so on RHEL-family images check /var/log/secure instead. Also look for new users, new sudoers entries, and unfamiliar cron jobs. If you find signs someone used the key, rotation alone is not enough: consider rebuilding from a known-good image and rotating anything else that key could have reached, because a key that was copied can be used from anywhere. And if the same key was used on other servers, rotate it on every one of them — a key is only as safe as its weakest copy.

6. Keep the next rotation boring

The cheapest rotation is the one you planned for. Keep one key per device or person, with a comment that names the device, and a short note of which key lives where — the next rotation is mostly a lookup exercise if the inventory exists. For new servers, put the current key in the first-boot setup instead of adding it by hand each time; our cloud-init first-boot guide covers verifying that automation before you trust it. A firewall rule that restricts SSH to your own address is a useful second layer while keys change; our firewall first-steps guide covers setting that up.

Checklist before you move on

  • New key generated on your own machine; the private key never left it.
  • New public key appended to authorized_keys, not overwrote.
  • New key tested from a second session while the first stayed open.
  • Old key line removed by fingerprint; old key tested and confirmed rejected.
  • Authorized keys, last logins, and the auth log checked if compromise was suspected.
  • Password login disabled only after the new key proved itself, if that is your setup.

Six checks, one order, no downtime. Once they pass, the old key is just a file on your machine waiting to be deleted — and the server only trusts the new one.

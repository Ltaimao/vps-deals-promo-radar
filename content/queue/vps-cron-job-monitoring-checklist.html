VPS Cron Job Silent Failures: Monitoring Checklist

Short answer: log every cron job's output, check its exit code, prevent overlapping runs with a lock, and add a heartbeat so a job that never runs is as visible as one that crashes. Cron is quiet by design: when a job fails, nothing on the server complains. Backups stop, certificates stop renewing, and cleanup jobs stop cleaning — and the first sign is usually the outage those jobs existed to prevent.

The failure modes are boring and predictable, which is good news: a log file, an exit-code check, a lock file, and a heartbeat cover nearly all of them. The checklist below turns a silent scheduler into one that reports.

1. Log output and check the exit code

By default, cron emails output to the local user — on a VPS that mail usually goes nowhere. Redirect each job's output to a log file, and make the job's success explicit rather than assumed: 

0 3 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1

A log full of output is only useful if someone reads it, so add an explicit failure check at the end of the script — or wrap the job so a non-zero exit sends an alert. The exit code is the one signal that distinguishes "ran and worked" from "ran and failed": a job that logs nothing and exits zero may still have done nothing, but a job that exits non-zero has definitely told you something is wrong.

2. Prevent overlapping runs with a lock file

A backup or sync job that takes longer than its interval will start a second copy while the first is still running — and the two copies can corrupt each other's output. Use flock so a new run skips itself if the previous one is still active: 

0 3 * * * flock -n /var/lock/backup.lock /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1

The -n flag means the second run exits immediately instead of waiting. Log that skip too, so a job that keeps skipping because it never finishes shows up in the log instead of silently falling behind.

3. Add a heartbeat for jobs that must run

Logs and exit codes catch a job that runs and fails. They cannot catch a job that never runs — a mistyped schedule, a daemon that stopped, a server that rebooted into a broken crontab. For jobs that must run, add a heartbeat: the job pings a monitoring endpoint at the end of a successful run, and the monitor alerts if the ping does not arrive on time: 

0 3 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1 && curl -fsS -m 10 https://hc-ping.example.com/backup-ok

Replace the URL with your own monitoring service. The heartbeat turns "nothing happened" into an alert, which is the one failure mode no log file can catch. Our uptime monitoring checklist covers the same idea for services — a check that only runs when things work is not a check.

4. Check the schedule, the environment, and the permissions

Most cron failures are not code failures. Cron runs with a minimal environment — a different PATH, no shell profile, a different working directory — so a script that works in your terminal may fail in cron for reasons that have nothing to do with its logic. Use absolute paths for every command and file, set any environment variables the script needs inside the script itself, and confirm the script is executable by the user that owns the crontab. After any edit, list the crontab and read the schedule back — a job scheduled for the wrong hour runs perfectly, at the wrong time.

5. Review the logs on a schedule, and alert on silence

A heartbeat alerts on a missed run; a weekly log review catches the slow drift — jobs that succeed but take twice as long as they used to, warnings that appear before a failure, a disk that fills because the cleanup job started skipping. Our disk space cleanup checklist covers what happens when the cleanup job is the one that stops. Put the review itself on a schedule, or it will be the next silent failure.

Checklist before you move on

  • Every job logs output to a file; failures exit non-zero and alert.
  • Long-running jobs use flock so overlapping runs cannot corrupt output.
  • Must-run jobs ping a heartbeat; a missed ping alerts.
  • Absolute paths, explicit environment, correct user and permissions for every job.
  • Crontab read back after every edit; logs reviewed weekly.

If a job has not logged anything in a while, do not assume it is fine — check whether it ran at all. Cron's silence is a feature for the scheduler and a hazard for the operator; the fix is a log, a lock, and a heartbeat.

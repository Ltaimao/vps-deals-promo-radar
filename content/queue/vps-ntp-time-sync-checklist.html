VPS Time Sync NTP Checklist

Short answer: read the clock and the offset first, confirm which sync service your image uses, enable that one service so it survives a reboot, and verify the offset is small afterwards. A server clock that drifts causes quiet problems later — log timestamps that do not line up, scheduled jobs that run at the wrong time, and TLS handshakes that fail because a certificate looks not yet valid or already expired. Five checks right after provisioning catch all of it, and they take a few minutes.

The commands below assume a Linux VPS. The sync service differs by image — chronyd on many RHEL-family and some Debian images, systemd-timesyncd on many Ubuntu images, ntpd on older setups — so the first job is finding out which one your server actually runs, not guessing.

1. Read the clock and the offset

Start with the current time and whether the system believes it is synchronized: 

timedatectl
date -u

timedatectl reports the local time, the universal time, and whether the system clock is synchronized. Compare the universal time against a clock you trust. If the offset is small — a fraction of a second — the clock is in good shape and the remaining steps are confirmation. If it is off by seconds or more, do not trust timestamps on this server yet; fix the sync before you install anything that depends on the time.

2. Find which service owns time sync

Only one service should manage the clock. Check what is running before you enable anything: 

systemctl status chronyd systemd-timesyncd ntpd --no-pager

One of them should show as active; the others should show as inactive or not found, depending on the image. If none is active, the server has no sync service running, which is the most common state on a fresh minimal image — move to step 3. If two are somehow active, stop and disable one of them first: two services adjusting the same clock will fight each other and the offset will never settle.

3. Enable the service so it survives a reboot

A service that is running but not enabled stops correcting the clock after the next reboot, and the drift comes back silently. Enable whichever service your image uses: 

sudo systemctl enable --now chronyd

Replace chronyd with systemd-timesyncd or ntpd if that is the service your image runs. The enable step is what makes the fix permanent; starting the service without enabling it only helps until the next reboot. If your provider's image documents a different time service, use the one it documents.

4. Verify the offset and the source

Give the service a moment to talk to its time source, then check the offset and which source it is using: 

chronyc tracking
chronyc sources

On a systemd-timesyncd system, timedatectl timesync-status shows the same idea. Look for a small offset and a reachable source. A source that never answers usually means the server cannot reach the time servers — check outbound UDP port 123 the way you would check any other outbound port before assuming the service is broken. A large offset that will not come down is a reason to investigate, not to force the clock: a sudden jump can confuse services that are already running, so correct it while the server is still empty.

5. Recheck after a reboot

Reboot once, then run the step 1 check again. This is the check that catches an enabled-but-not-actually-starting service and a clock that resets on boot, which happens on some virtualized images. If the clock is right after the reboot and the service shows as active, the setup is done. If the time is wrong again, the service is not starting at boot — go back to step 3 and confirm the enable step took.

If you rebuild servers from a template, put the sync-service check into the first-boot setup so every fresh server gets the same clock without a manual repeat. Checklist before you move on

  • The clock matches a trusted time source, with only a small offset.
  • Exactly one sync service is active — chronyd, systemd-timesyncd, or ntpd.
  • That service is enabled, so it starts on boot.
  • The offset is small and the time source answers.
  • The clock is still right after a reboot.

Five checks, one order, no extra software to install. Once they pass, logs, scheduled jobs, and certificates all share the same time, and the server is ready for the actual work you bought it for.

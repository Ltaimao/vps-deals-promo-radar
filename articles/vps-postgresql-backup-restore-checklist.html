PostgreSQL Backup and Restore Checklist for Your VPS

Short answer: take a logical dump with pg_dump, copy it off the server, keep the roles and permissions with it, and restore it on a scratch database regularly — a backup you have never restored is a guess, not a safety net. PostgreSQL stores your data in a cluster directory that a plain file copy cannot safely capture while the server is running, so the dump is the unit that matters. The checklist below turns "we have backups" into something you can prove on a quiet afternoon instead of discovering during an outage.

The failure modes are unglamorous: a dump that ran but captured nothing, a backup sitting on the same disk as the database it protects, a restore that fails because the roles were never saved. Each one is cheap to prevent and expensive to discover late.

1. Dump the database, and the roles with it

A logical dump with pg_dump reads the database through the server, so it stays consistent while the application keeps running. Dump each database you care about, and dump the roles separately — a database restore will fail or silently lose ownership if the roles it references do not exist on the target: 

pg_dump -U postgres -d myapp > /var/backups/myapp.sql
pg_dumpall --roles-only -U postgres > /var/backups/roles.sql

If the database is large, compress the dump as you write it, and consider pg_dump in custom format with parallel jobs for a faster restore later. Our MySQL backup and restore checklist covers the same principle for the other common database: the dump is only half the job, the restore is the other half.

2. Copy the dump off the server the same day

A backup on the same disk as the database protects against a deleted table, not against a dead disk, a full disk, or a compromised server. Copy each dump to a second location — another server, object storage, or an offsite backup account — before the day ends, and keep at least one copy that the database server itself cannot delete. Our offsite backup rotation checklist covers retention and rotation so old copies do not quietly pile up until the backup disk fills.

Verify the copy, not just the transfer: compare checksums or at least file sizes between the server copy and the offsite copy. A transfer that reported success and wrote a truncated file is worse than a transfer that failed loudly, because it looks like a backup until the day you need it.

3. Restore on a scratch database, on a schedule

The restore test is the whole point of the exercise. Create an empty database on a test machine or a spare VPS, restore the dump into it, and confirm the application can read what it expects — row counts for the tables that matter, a login with the application role, a query that touches the newest data: 

createdb -U postgres myapp_test
psql -U postgres -d myapp_test < /var/backups/myapp.sql

Run this test on a schedule, not once. Dumps rot: a new extension, a new role, a table that outgrew the backup window — any of these can turn a working backup routine into a failing one without changing a single line of the backup script. A monthly restore test catches that drift while it is still boring.

4. Watch the backup window and the disk it writes to

A dump that takes longer than the window you gave it will either overlap the next backup or get killed halfway — either way you end up with no usable copy for that day. Watch how long the dump takes as the database grows, and watch the disk the dump lands on: a backup that fills the disk can take the database down with it. Keep the backup target on its own volume when you can, and alert on free space before it becomes the outage. If the dump is getting slow, the custom format with parallel restore is usually the first fix worth trying.

5. Write down the restore steps before you need them

During an outage nobody should be reconstructing the restore procedure from memory. Write the steps down — which dump to fetch, which roles file to load first, the exact commands, and how to point the application at the restored database — and keep that document where you can reach it when the server is down. A restore runbook that has been followed once, on a scratch database, is worth more than a backup policy document that has never been tested.

Checklist before you move on

  • Each database has a scheduled pg_dump; roles are dumped separately.
  • Every dump is copied off the server the same day, with checksums verified.
  • A restore into a scratch database is tested on a schedule, with the application able to read the result.
  • Dump duration and backup-disk free space are monitored as the database grows.
  • Restore steps are written down and reachable when the server is down.

If you cannot point to the last successful restore test, the backup routine is unfinished — schedule the test before the next backup, not after the next outage.
